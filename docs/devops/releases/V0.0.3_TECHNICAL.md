## Conformite RGPD waitlist (NG-009)

- **Mention de transparence (art. 13)** au point de collecte de l'email :
  finalite transactionnelle (envoi de la cle d'acces) + lien vers la politique
  de confidentialite.
- **Consentement marketing explicite (art. 6/7)** : checkbox opt-in **decochee
  par defaut**, separee de l'email transactionnel. Seuls les emails ayant
  consenti pourront etre importes dans l'outil d'emailing.
- **DB** : colonnes `marketing_consent` + `marketing_consent_at` sur
  `beta_waitlist`. L'horodatage de preuve (art. 7.1) est pose **cote serveur par
  trigger**, jamais transmis par le client (anti-falsification).
- **Politique de confidentialite** (section 9) : declaration des sous-traitants
  email (MailerSend transactionnel, MailerLite marketing), date maj 2026-06-23.

## Securite : send-waitlist-confirmation (NG-007)

- L'Edge Function (`verify_jwt:false`, appelee par trigger DB) etait publiquement
  atteignable : risque d'envoi d'emails brandes arbitraires (abus + quota Resend).
- **Correctif** : secret partage. La fonction exige un header `x-waitlist-secret`
  egal a l'env `WAITLIST_TRIGGER_SECRET` (comparaison a temps constant). Le
  trigger lit le secret depuis Supabase Vault et le transmet.
- **Rollout progressif** : tant que le secret n'est pas pose (Vault + env), le
  comportement est inchange (header omis + warning). Une fois pose des deux
  cotes, le secret devient obligatoire (401 sinon). Aucune rupture.
