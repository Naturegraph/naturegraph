# V0.7.11 : la sonde de reprise teste le VRAI appel qui pend (supabase-js)

## Pourquoi 0.7.10 ne suffisait pas

0.7.10 sondait le backend au retour d'arriere-plan avec un `fetch` reseau BRUT
(`/auth/v1/health`, no-cors). Sentry prod (release 0.7.10) montre que ca n'a pas
suffi : `session-timeout-on-continue` continue d'apparaitre (le `getUser()` de
`assertActiveSession` pend toujours 8 s) SANS que la page se recharge. Conclusion :
le TCP repond (la sonde brute reussit), mais c'est le **client supabase-js lui-meme**
qui reste bloque sur `getUser()`. On sondait la mauvaise chose.

## Le fix

`resumeRecovery.ts` : la sonde teste desormais **l'appel exact qui pend**,
`supabase.auth.getUser()`, borne par un timeout de 5 s. Distinction cle :

- getUser() qui **resout OU rejette** dans le delai = le serveur a repondu = client
  vivant -> aucun reload (l'app sait gerer une erreur).
- getUser() qui **depasse le timeout** (aucune reponse) = client bloque -> **reload
  une fois** (garde anti-boucle 10 s) pour repartir sur un client + des sockets neufs
  (= la "relance complete" qui debloquait, desormais automatique). Brouillon (NG-004)
  - photos (NG-038) restaures : aucune perte.
