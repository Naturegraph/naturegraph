# V0.7.8 : le « bouton Partager mort » du va-et-vient, corrige aux deux causes

## Resume

Depuis des semaines, le bouton Publier / Partager restait « mort » apres un
va-et-vient mobile (mettre l'app en arriere-plan, ex. ouvrir Instagram, puis
revenir). Les releases 0.7.3 a 0.7.7 traitaient la piste « page gelee -> reload ».
Cette version corrige les DEUX vraies causes, identifiees avec preuves.

## Ce qu'on savait enfin (preuves)

Retours Nicolas + captures Sentry :

- **Instant Nature** : va-et-vient -> rien ; relance complete -> « impossible de
  partager ». Sentry (release 0.7.6) montre sur la relance :
  `[postService.createPost] erreur DB: TypeError: Load failed` sur
  `POST /rest/v1/posts`, depuis le navigateur in-app Instagram (iPhone, iOS 26.5).
- **Rencontre Nature** : va-et-vient -> rien ; relance -> marche. Et **aucune**
  erreur dans le feed Sentry, alors que c'est la forme la plus utilisee.
- Dans le panneau et ailleurs, tout repond : le bouton « Suivant » (etape 2->3)
  marche. Seul « Partager » est mort.

Deux comportements differents = deux causes.

## Cause 1 (Instant) : la 1ere requete reseau meurt au reveil

`TypeError: Load failed` = l'erreur WebKit/Safari d'un fetch reseau qui echoue.
Au reveil, iOS a tue la connexion TLS : la **1ere** requete du pipeline (le POST
qui cree le post) part sur une socket morte et rejette. Or `createPost` n'avait
**aucun retry** (seul l'upload des photos en avait). Un echec = fini.

**Fix** :

- `classifyError` reconnait desormais les libelles reseau WebKit (`Load failed`,
  `network connection was lost`, `cancelled`, `timed out`) comme erreurs `network`.
- Le POST `createPost` / `updatePost` est **retente jusqu'a 3x** sur erreur
  reseau/timeout (backoff 1s, 2s). La 2e tentative ouvre une connexion fraiche et
  passe. On NE retente PAS les erreurs auth/4xx/5xx (definitif ou risque de
  doublon d'INSERT). Marche partout : PWA, navigateur in-app, desktop.

## Cause 2 (Rencontre) : blocage silencieux sur un etat React perime

Le composant Rencontre bloquait la publication si `user?.id` (etat React du
contexte Auth) etait vide. Au reveil, ce contexte se re-hydrate et `user.id` peut
etre momentanement vide **alors que la vraie session Supabase est encore vivante**.
Le garde posait alors une erreur sur le champ _description_, invisible a l'etape 3
-> « rien ne se passe ». Et comme c'etait un simple `trackFailure` (Warning), rien
dans le feed d'erreurs Sentry. Instant n'avait pas ce garde -> il allait, lui,
jusqu'au reseau (d'ou la difference de symptome).

**Fix** : la source de verite de l'auteur devient la **session vivante**, plus
l'etat React.

- Suppression du garde `!user?.id` du composant Rencontre et du hook.
- Le hook derive l'id auteur de `assertActiveSession()` (qui **repare** la session
  par refresh de l'access token expire, au lieu de bloquer) et l'utilise pour
  l'upload media.
- `postService.createPost` derive `user_id` de `supabase.auth.getUser()` (l'id que
  verifie la RLS `auth.uid()`), avec repli sur l'id passe si offline.
- Tout echec restant est desormais soit **visible** (toast d'erreur), soit une
  **redirection claire** vers /login (refresh token vraiment mort) : plus jamais
  de bouton muet.

## Fichiers

- `src/hooks/useContributePostSubmit.ts` : retry reseau du POST, classifyError
  elargi, auteur = session vivante (authorId), suppression du garde `!user?.id`.
- `src/services/postService.ts` : `createPost` derive l'auteur de la session.
- `src/components/contribute/ContributeEncounterForm.tsx` : suppression du bail
  silencieux `!user?.id`.

## Risque connu, assume

Le retry reseau du POST peut, dans un cas rare (INSERT commit cote serveur mais
reponse perdue), creer un doublon de post. Choix assume : bien preferable a un
bouton totalement mort. L'utilisateur peut supprimer un doublon ; le cas est rare
(« Load failed » est le plus souvent un echec d'envoi, avant commit).
