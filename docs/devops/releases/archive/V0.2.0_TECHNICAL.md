> Statut : **EN ATTENTE DE VALIDATION NICOLAS**. Ne pas merger vers `main` avant son OK explicite.
> Periode couverte : 2026-07-09 (V0.1.2) au 2026-07-21.
> 19 commits sur `develop`, du sprint securite/infra 8 tickets.

---

## 1. Pourquoi MINEUR et pas PATCH

`VERSIONING.md` : "une feature ajoutee -> MINEUR". Cette release ajoute plusieurs
briques qui n'existaient pas (sauvegarde des photos, surveillance des quotas,
webhooks Resend, blocage des emails jetables, alertes de moderation). Ce ne sont
pas des correctifs, ce sont des capacites nouvelles. D'ou **V0.1.2 -> V0.2.0**.

Note : le tableau des jalons de `VERSIONING.md` annonce V0.2.0 comme
"post-lancement : accessibilite + eco-conception + metriques". Le contenu reel
est different (securite + resilience). Le tableau est previsionnel, pas normatif,
mais il merite d'etre reajuste.

---

## 2. Particularite majeure de cette release

**L'essentiel du travail est DEJA en production.** Les migrations SQL et les Edge
Functions ont ete appliquees directement sur le projet prod `hrxgduvworofnrjmgpcj`
au fil du sprint, puisque c'est la seule base reelle (cf. NG-007).

Consequences a bien avoir en tete :

| Element                       | Deja en prod ? | Part au merge ? |
| ----------------------------- | -------------- | --------------- |
| 8 migrations SQL              | ✅ Oui         | Non             |
| Edge Functions (10 touchees)  | ✅ Oui         | Non             |
| Templates email Supabase Auth | ✅ Oui         | Non             |
| Crons pg_cron                 | ✅ Oui         | Non             |
| Code front (src/)             | ❌ Non         | ✅ Oui          |

Le merge `develop -> main` ne livre donc que **6 fichiers front**. C'est une
release a faible risque technique, mais aussi a faible visibilite : l'essentiel
tourne deja depuis plusieurs jours et a ete observe en conditions reelles.

**Corollaire important pour le rollback** : revenir en arriere sur le code ne
revient PAS en arriere sur la base ni sur les Edge Functions. Les deux plans de
rollback sont independants (cf. section 6).

## 3. Contenu par ticket

### NG-001, validation serveur des medias (securite)

- `validate-media` (Edge Function) + module pur `mediaMagic.ts`.
- Lit les magic bytes reels du fichier : JPEG/PNG/WebP/MP4 acceptes,
  TIFF/GIF/BMP/HEIC/AVIF refuses. Format inconnu = laisse passer (fail-open
  assume, pour ne jamais bloquer une photo legitime).
- Trigger `validate_media_on_write` sur `public.media` (INSERT/UPDATE OF url),
  et non sur `storage.objects` : le client televerse le fichier PUIS insere la
  ligne, declencher sur le storage creait une course.
- 18 tests unitaires (`src/utils/serverMediaMagic.test.ts`).
- **Verifie en conditions reelles** : un TIFF renomme en .jpg avec un
  `Content-Type: image/jpeg` force est bien accepte par le storage, puis supprime
  par le trigger, avec `status='invalid'` et 404 a l'origine.

### NG-041, cloisonnement des Edge Functions

- `rejectDisallowedOrigin()` dans `_shared/cors.ts` : 403 sur toute origine non
  autorisee. Les appels serveur (sans en-tete Origin) passent.
- Branche sur les 5 fonctions appelees depuis le navigateur.
- **Ecart assume avec le brief** : le brief demandait `--no-verify-jwt`. Non
  applique, ce serait une regression de securite. Le `verify_jwt` existant de
  chaque fonction est conserve.
- Alerte pic d'inscriptions > 50/h : trigger sur `auth.users` -> `alert-signup-surge`.
  Le trigger avale ses propres erreurs (`EXCEPTION WHEN OTHERS THEN RETURN NEW`) :
  une panne d'alerte ne doit jamais casser une inscription.

### NG-036, moderation a l'echelle

- Alerte email immediate sur signalement (`notify-new-report`), avec drapeau
  urgent si plus de 3 signalements sur le meme contenu en 1 h.
- **Attention** : la table vivante est `moderation_reports`. La table `reports`
  est un vestige orphelin, ne pas s'y brancher.
- Blocage des emails jetables a l'inscription : table `email_blocklist`
  (30 domaines) + hook Auth "Before User Created". Teste : mailinator -> 403,
  gmail -> passe. Aucun fournisseur grand public n'est bloque.
- Filtre par type de contenu dans la file de moderation admin.
- Rate limits natifs Supabase regles (5 inscriptions / 5 min / IP).

### NG-035, observabilite des emails

- `resend-webhook` : reception des evenements Resend, signature **Svix verifiee**
  (HMAC-SHA256, tolerance de rejeu 5 min, comparaison a temps constant), fail
  closed si le secret manque. Journalise dans `email_events`, dedoublonne par
  index unique.
- Motivation : `email_send_log` sous-estimait le volume reel de **43 %**
  (347 envois Resend contre 197 journalises), car les codes de connexion Supabase
  partent aussi par Resend en SMTP sans passer par notre dispatcher.
- Alertes taux de rejet > 2 % et plaintes spam > 0,1 % sur 7 jours glissants,
  avec volume minimum de 20 envois pour eviter les faux positifs.

### NG-037, resilience

- `ROLLBACK_OPEN_ACCESS.md` : 3 niveaux d'urgence. Point cle documente,
  `OPEN_ACCESS_ENABLED` est une **constante en dur** dans `featureFlags.ts`, pas
  une variable d'environnement : le vrai coupe-circuit rapide est le reglage
  Supabase Auth "Allow new users to sign up".
- `check_infra_health()` + `alert-infra-health`, cron quotidien 16 h UTC.
  Surveille : quota Resend journalier (70 %) et mensuel (66 %), connexions
  Postgres, taille de base, storage, rejets, plaintes. Anti-spam de 20 h.
- **Sauvegarde des photos** : les sauvegardes Supabase n'incluent PAS le Storage.
  331 fichiers (159 Mo) etaient sans aucune protection. Miroir append-only cree
  (bucket prive `media-backup`, `media_backup_log`, cron 5 h UTC).
  Integrite verifiee : 0 copie absente, 0 taille differente.
- `RESTAURATION_BACKUP.md` : procedure documentee, **non executee** (une
  restauration cree un projet facture).

### NG-030, emails de cycle de vie (reduit)

Ticket volontairement **reduit** apres constat que la moitie etait perimee :
la relance J+3 existait deja (E5), les references beta ne vivaient que dans le
template d'invitation devenu mort, le template Reauthentication ne sert qu'aux
flux avec mot de passe (inexistants en OTP).

- Template FR "Change Email Address" cree et applique.
  **Ce flux fonctionne par LIEN**, donc `{{ .ConfirmationURL }}` et surtout pas
  `{{ .Token }}` : aucun ecran ne permet de saisir un code de changement d'email.
- "Secure email change" est ACTIF : les DEUX adresses doivent confirmer. Le
  message de l'app n'en annoncait qu'une, corrige.
- "Email OTP expiration" vaut 600 s, les templates annoncaient 2 minutes.
  Aligne a 10 minutes. Enjeu concret : un utilisateur qui croit son code perime
  en redemande un, et chaque redemande consomme le quota Resend journalier.
- **mail-tester : 9,6/10** (cible >= 9). SPF, DKIM, DMARC valides.

### Divers

- Quota marketing E1-E4 : 1 -> **2 emails par semaine**.
- NG-042 : les erreurs RPC de recherche taxonomique ne retombent plus sur un
  `return []` silencieux, qui affichait un faux "Aucune espece trouvee".
- Filtrage du bruit Sentry des navigateurs in-app (Instagram, Facebook).

## 6. Plan de rollback

**Code** : `git revert` du merge, redeploiement Vercel. Ne concerne que les
6 fichiers front, sans effet sur la base.

**Base et Edge Functions** (independants du code) :

- Alertes trop bavardes : `SELECT cron.unschedule('daily_infra_health');`
- Sauvegarde photos : `SELECT cron.unschedule('daily_media_backup');`
  **Ne JAMAIS supprimer le bucket `media-backup`** sans autre copie verifiee.
- Blocage emails jetables : desactiver le hook au dashboard.
- Validation des medias : `DROP TRIGGER validate_media_on_write ON public.media;`
