## 1. Note technique

### 1.1 NotReadableError a l'upload photo (bloquait la publication)

Cause : la photo choisie redevient **illisible au moment de lire ses octets**
(reference OS perimee, permission revoquee, photo cloud pas encore telechargee).
C'est un etat de l'appareil, pas un bug de notre code. Traitement en 2 couches :

- **Prevention** (`EncounterStep1.handleFiles`, partage Encounter + Instant) : des
  la selection, on lit les octets de chaque photo (reference fraiche) et on
  reconstruit un `File` 100 % en memoire. La reference OS ne peut plus se perimer
  d'ici l'upload. Si la lecture echoue des la selection (rare), on le signale
  immediatement photo par photo.
- **Filet** (`useContributePostSubmit`) : si une lecture echoue malgre tout a
  l'upload, message ACTIONNABLE (« re-selectionne la photo ») + remontee en
  `warning` (trackFailure) au lieu d'une issue d'erreur Sentry.

### 1.2 « Utilisateur non connecte » au clic sur J'adore depuis un profil

`ProfileFeed` ne passait pas `canInteract`, donc un visiteur anonyme (liens publics
NG-054) declenchait la mutation de reaction -> `throw` capture par le filet global.
Fix : `canInteract={isAuthenticated}` (comme le feed et PostDetail) + garde-fou dans
`handleReact`. L'invite est desormais redirige vers /signup.

### 1.3 AbortError a l'upload = bruit Sentry

Abandon attendu (watchdog delai depasse ou annulation), pas un crash. -> message
timeout clair + `trackFailure` warning (plus de fausse issue d'erreur).

### 1.4 Verifie mais NON modifie

- **Timeout recherche espece** (issue « echec silencieux search.species ») :
  l'utilisateur voit deja un message clair (« Connexion lente ou interrompue... »)
  via `setHasNetworkError`. C'est un timeout reseau (la requete est a ~51 ms depuis
  NG-064). Aucun code a changer.
- **Lazy EchangesSection** (chunk perime) : deja mitige par le reload
  `vite:preloadError` (V0.6.9), attrape par SectionErrorBoundary. A surveiller.
