# V0.7.9 : LA cause du bouton mort enfin trouvee (verification de session sans timeout)

## Ce qui a change dans la comprehension

V0.7.8 corrigeait deux vraies causes (retry reseau du POST, auteur = session
vivante), mais le va-et-vient restait mort en test reel. En reprenant le pipeline
a froid, on a trouve la cause de fond, presente depuis le tout debut et jamais
traitee par 0.7.3 -> 0.7.8.

## La cause reelle : `assertActiveSession()` PEND sur une socket morte

Dans `submit()`, on faisait `await assertActiveSession()` **avant** d'afficher le
moindre retour visuel (`setIsSubmitting(true)` venait APRES). Or
`assertActiveSession` appelle `supabase.auth.getUser()` puis, si besoin,
`refreshSession()` : **aucun de ces appels n'a de timeout cote client**.

Au retour d'arriere-plan, la connexion TLS est morte mais la socket peut rester
« a moitie ouverte » : le fetch ne rejette pas vite, il **PEND** (jusqu'au timeout
TCP de l'OS, 30-60 s ou plus). Consequence :

- `submit()` reste bloque **avant** le spinner -> **ni spinner, ni erreur**.
- Rien n'est jete -> **rien dans Sentry** (meme quand Sentry est actif).
- Un 2e tap relance un appel qui pend aussi -> le bouton parait totalement mort.
- Une relance complete de l'app (nouveau process, nouvelle socket) repart : d'ou
  « ca marche seulement en relancant tout ».

Symptome identique sur Rencontre ET Instant, et parfaitement coherent avec tous
les retours (« rien ne se passe », « rien sur Sentry », « il faut relancer »).

## Le fix

Dans `useContributePostSubmit.ts` :

1. **Verrou + spinner AVANT tout appel reseau.** On pose `inFlightRef` et
   `setIsSubmitting(true)` tout de suite : le bouton donne un retour immediat et un
   2e tap est bloque proprement (toast « deja en cours »).
2. **Timeout sur la verification de session.** `assertActiveSession()` est
   enveloppe dans `withTimeout(..., 8s)`. S'il pend, on ne bloque plus : on retombe
   sur l'id React et on laisse `createPost` re-deriver l'auteur cote serveur +
   retenter sur erreur reseau. En cas de vrai echec sans id, message VISIBLE.
3. Les retours anticipes relachent proprement le verrou + le spinner (helper
   `releaseIfCurrent`, protege par l'epoch anti-zombie).

Dans `postService.ts` : le `getUser()` de `createPost` (ajoute en 0.7.8) est lui
aussi borne par une course avec un timeout (5 s) + repli sur l'id passe, pour ne
jamais geler la creation du post.

## Garanties

- Le bouton Partager donne **toujours** un retour en quelques secondes maximum :
  spinner immediat, puis succes, ou message d'erreur clair. **Plus jamais de bouton
  muet.**
- Cumule avec 0.7.8 : le POST est retente sur erreur reseau (« Load failed » iOS),
  et l'auteur vient de la session vivante.

## Fichiers

- `src/hooks/useContributePostSubmit.ts` : verrou + spinner immediats, timeout 8 s
  sur `assertActiveSession`, helper `releaseIfCurrent`.
- `src/services/postService.ts` : timeout 5 s sur le `getUser()` de `createPost`.

## Note environnement (Preview vs Prod)

Le diagnostic Sentry doit se faire en **prod** : Sentry ne s'active que si
`VITE_SENTRY_DSN` est defini, variable qui peut ne pas etre presente sur
l'environnement Preview de Vercel (d'ou « rien sur Sentry » sur l'URL de preview).
Le theme sombre different sur la preview vient d'un origin neuf (aucune preference
de theme enregistree dans le localStorage de ce domaine) : cosmetique, sans lien
avec la publication.
