## Phase 1 - Stabilite immediate

### 1. Toast persistant pour erreurs reseau

**Probleme** : les toasts d erreur disparaissaient apres 4.5s auto-dismiss.
Si l user etait en train de regarder ailleurs (photo, scroll), il ratait
l info et croyait que la submit avait reussi.

**Fix** :
- `ToastContext` ajoute un parametre `options.persistent?: boolean`.
- Persistent = pas d auto-dismiss + progress bar masquee. L user doit
  cliquer la croix pour fermer.
- A utiliser sur les erreurs critiques : echec submit, perte de connexion,
  conflit donnees, etc. Toast.error simple reste auto-dismiss 4.5s.

### 2. Indicateur online/offline global

**Probleme** : quand le wifi/4G tombait, les requetes timeout silencieusement
et l user croyait que "l app etait cassee".

**Fix** :
- Nouveau composant `OnlineStatusBanner` rendu globalement dans `main.tsx`.
- Detection via `navigator.onLine` + listeners `online` / `offline`.
- Bandeau rouge "Hors ligne, tes actions ne seront pas enregistrees"
  quand connexion tombe.
- Bandeau vert "Connexion retablie" pendant 3s au retour, puis disparait.
- Au retour online : `queryClient.invalidateQueries()` automatique pour
  refetch les data fraiches.

### 3. Refetch automatique focus + delai 5 min

**Probleme** : V1.1.3 avait `refetchOnWindowFocus: false` par precaution
contre les races mutations. Mais cela laissait des donnees stales quand
l user revenait sur l onglet apres 30+ min.

**Fix** :
- `queryClient` : `refetchOnWindowFocus: true` + `staleTime: 5 * 60 * 1000`.
- Avec staleTime 5min, le focus refetch ne se declenche que si les data
  sont stales (5 min), ce qui evite les races sur les mutations en cours.
- `refetchOnReconnect: true` : refetch automatique au retour de connexion.

### 4. Retry automatique 5xx Supabase avec backoff

**Probleme** : Supabase peut renvoyer des 502/503 sous charge ou
maintenance. V1.1.3 echouait au premier coup -> l user voyait une erreur
generique sans comprendre que c etait transient.

**Fix** :
- Helper `is5xxError()` qui detecte les codes 5xx + patterns PostgREST.
- `queryClient.defaultOptions.queries.retry` devient une fonction qui
  retente jusqu a 3 fois UNIQUEMENT si l erreur est 5xx.
- `retryDelay` : backoff exponentiel 1s / 2s / 4s (cap 30s).
- Erreurs 4xx (auth, validation, RLS) : pas de retry (la cause ne va pas
  disparaitre).
- Mutations : retry desactive (risque doublons cote serveur).

## NG-004 finalisation

### Refresh session proactif au visibility change

**Symptomes adresses** :
- #2 Session instable (besoin re-saisir code login regulierement)
- #3 Perte d etat authentifie (user connecte mais "perdu" dans le flow)
- #4 Features intermittentes (parfois non fonctionnels jusqu a refresh)

**Cause probable** : le refresh token Supabase a une duree de vie. Le
refresh interval ne se declenchait que toutes les 30 min. Si l user
revenait sur l onglet apres 1h+ d absence, le token pouvait etre expire,
les requetes echouaient sans message clair, l UI semblait "cassee".

**Fix** :
- `AuthContext` listener sur `document.visibilitychange`.
- Au passage `visible` : refresh la session si la derniere maj > 10 min.
- Throttle 10 min entre 2 refresh pour ne pas spammer.
- Si refresh token mort detecte : signOut local propre + redirect login
  (au lieu de boucle infinie de retry).

## Risques

Faible. Les changements sont :

- ToastContext : retro-compatible (option optionnelle).
- OnlineStatusBanner : composant nouveau, no-op si toujours en ligne.
- queryClient : retry + focus refetch sont des comportements standard
  React Query, testes par la communaute.
- AuthContext visibility change : throttle 10 min evite le spam.

Surveillance recommandee 48h post-deploiement :

- Logs Supabase pour pic de refresh sessions au visibility change
- Taux d erreur 5xx (si Supabase down, les retries peuvent saturer)
- Aucun toast persistent "fantome" qui resterait affiche en boucle
